NestJS vs Next.js — 헷갈리기 쉬운 차이

이름이 비슷하지만 완전히 다른 프레임워크입니다!

NestJS (우리 프로젝트) Next.js
역할 백엔드 전용 API 서버 React 프론트엔드 + 간단한 백엔드
구조 Module → Controller → Service Pages / App Router
용도 복잡한 API, 마이크로서비스 웹사이트 (SSR/SSG)
비유 🧑‍🍳 전문 요리사
(복잡한 요리 전문)		 👨‍🍳 만능 셰프
(요리도 서빙도 가능)
💡 우리가 NestJS를 선택한 이유:
대규모 CMS에는 구조화된 아키텍처가 필요합니다. NestJS는 기능별로 모듈을 깔끔하게 분리할 수 있고, TypeScript를 강제하여 타입 안전성을 보장합니다.

실전: 사용자 관리 기능의 폴더 구조

하나의 기능을 만들 때 생성하는 파일들입니다.

backend/src/user/
├── dto/
│    ├── create-user.dto.ts ← 생성 시 데이터 검증 규칙
│    └── update-user.dto.ts ← 수정 시 데이터 검증 규칙
├── user.controller.ts ← HTTP 요청 수신 (라우터)
├── user.service.ts ← 비즈니스 로직 (DB 작업)
└── user.module.ts ← 모듈 등록 (조립)

개발 순서

  1. DTO 작성 — "이메일은 필수, 비밀번호는 8자 이상" 규칙 정의
  2. Service 작성 — DB 조회/생성/수정/삭제 로직 구현
  3. Controller 작성 — "POST /users → Service.create() 호출" 연결
  4. Module 작성 — Controller와 Service를 하나로 묶기
  5. AppModule에 등록 — 전체 앱에 이 기능 추가
5

왜 DTO → Service → Controller → Module 순서일까?

"큰 틀(Module)부터 만드는 게 자연스럽지 않나?" 라고 생각할 수 있습니다.
하지만 핵심은 "누가 누구를 필요로 하는가" (의존성 방향)입니다.

의존성 관계 // Service가 DTO를 사용함 → DTO가 먼저 있어야 함 class UserService { create(dto: CreateUserDto) { ... } // ← CreateUserDto가 뭔지 알아야 쓸 수 있음 } // Controller가 Service를 사용함 → Service가 먼저 있어야 함 class UserController { constructor(private userService: UserService) {} // ← UserService가 뭔지 알아야 함 } // Module이 Controller, Service를 등록함 → 둘 다 먼저 있어야 함 @Module({ controllers: [UserController], // ← UserController가 뭔지 알아야 함 providers: [UserService], // ← UserService가 뭔지 알아야 함 }) class UserModule {}

React로 비유하면 똑같습니다

1. 유틸 함수
lib/media-utils.js
→
2. 컴포넌트
MediaList.jsx
(유틸을 import)
→
3. 라우터 등록
App.jsx
(컴포넌트를 import)

App.jsx에 <Route element={<MediaList/>}> 먼저 쓰면? → MediaList가 없으니 에러!

NestJS도 같은 원리 — 아래에서 위로 쌓기

1. DTO
재료 준비
(= Zod 스키마)
→
2. Service
로직 구현
(= lib/ 함수)
→
3. Controller
요청 연결
(= Page 컴포넌트)
→
4. Module
묶기
→
5. AppModule
전체 등록
(= App.jsx Route)
🏗️ 건물 비유: 지붕(Module)부터 안 만들고, 기초(DTO) → 벽(Service) → 문(Controller) → 지붕(Module) → 도로 연결(AppModule) 순서로 쌓아올립니다.

Controller — 요청을 받는 문지기

HTTP 요청을 받아서 Service에게 전달합니다. React의 페이지 컴포넌트(라우터)와 비슷합니다.

user.controller.ts @Controller('users') // 이 컨트롤러는 /users 경로 담당 @UseGuards(JwtAuthGuard) // 모든 요청에 로그인 필수 export class UserController { constructor(private readonly userService: UserService) {} // ↑ NestJS가 자동으로 UserService를 넣어줌 // React의 useContext()와 비슷한 개념! @Post() // POST /users @Permissions('user:create', '*') // 권한 확인 create(@Body() dto: CreateUserDto) { // ↑ 요청 body를 가져옴 (React에서 form data 가져오는 것과 비슷) return this.userService.create(dto); } @Get(':id') // GET /users/abc123 (동적 라우트) findOne(@Param('id') id: string) { // ↑ React Router의 useParams()와 같은 역할! return this.userService.findOne(id); } }

HTTP 메서드 ↔ 프론트엔드 호출 매핑

NestJS 데코레이터 HTTP 용도 프론트엔드 호출
@Post() POST 생성 api.post('/users', data)
@Get() GET 목록 조회 api.get('/users')
@Get(':id') GET 단일 조회 api.get('/users/abc123')
@Patch(':id') PATCH 부분 수정 api.patch('/users/abc123', data)
@Delete(':id') DELETE 삭제 api.delete('/users/abc123')

파라미터 가져오기

NestJS 데코레이터 가져오는 위치 예시
@Body() 요청 body (JSON) { "name": "홍길동" }
@Param('id') URL 경로 /users/abc123
@Query('page') 쿼리 스트링 /users?page=2
@CurrentUser('id') JWT 토큰 현재 로그인한 사용자 ID

Service — 실제 일을 하는 일꾼

DB 조회, 데이터 가공, 규칙 검증 등 모든 "일"이 여기서 이루어집니다.

user.service.ts — 사용자 생성 async create(dto: CreateUserDto) { // 1. 이메일 중복 확인 const existing = await this.prisma.user.findUnique({ where: { email: dto.email } }); if (existing) { throw new ConflictException('이미 사용 중인 이메일입니다'); // → 자동으로 HTTP 409 응답! } // 2. 비밀번호 암호화 (절대 평문 저장 금지!) const hashed = await bcrypt.hash(dto.password, 10); // "password123" → "$2b$10$xK3b..." 로 변환 // 3. DB에 저장 const user = await this.prisma.user.create({ data: { email: dto.email, password: hashed, name: dto.name } }); return user; }
⚠️ async/await란?
DB 조회는 시간이 걸리는 작업입니다. await는 "결과가 올 때까지 기다려"라는 의미입니다.
React에서도 await api.get(...) 쓰시죠? 같은 원리입니다!
8

에러 처리 — throw 하면 자동 응답

NestJS는 특별한 에러 클래스를 제공합니다. throw하면 자동으로 해당 HTTP 상태 코드로 응답됩니다.

백엔드 (throw)

throw new NotFoundException( '사용자를 찾을 수 없습니다' ); // → HTTP 404 throw new ConflictException( '이미 사용 중인 이메일입니다' ); // → HTTP 409 throw new BadRequestException( '자기 자신은 삭제할 수 없습니다' ); // → HTTP 400 throw new ForbiddenException( '권한이 없습니다' ); // → HTTP 403

프론트엔드 (catch)

try { await api.post('/users', data); } catch (error) { const status = error.response?.status; // 404, 409, 400, 403 const message = error.response?.data?.message; // "이미 사용 중인 이메일입니다" alert(message); }
💡 핵심: 백엔드에서 throw 하면 NestJS가 알아서 적절한 HTTP 응답을 만들어줍니다. 프론트엔드는 catch에서 에러 메시지를 꺼내 쓰면 됩니다.

DTO vs Zod — 데이터 검증 비교

같은 목적, 다른 문법. 프론트의 Zod와 백엔드의 DTO를 나란히 비교합니다.

React Zod 스키마

const schema = z.object({ email: z.string() .email('이메일 형식 오류'), password: z.string() .min(8, '8자 이상'), name: z.string() .min(1, '이름 필수'), type: z.enum([ 'ADMIN', 'MEMBER' ]), });

NestJS DTO

export class CreateUserDto { @IsEmail({}, { message: '이메일 형식 오류' }) email: string; @MinLength(8, { message: '8자 이상' }) password: string; @IsNotEmpty() name: string; @IsEnum(UserType) type?: UserType; }
❓ 왜 프론트와 백엔드 양쪽에서 검증할까?
• 프론트 검증: 사용자 경험 (빠른 피드백, 제출 전 확인)
• 백엔드 검증: 보안 (프론트 검증은 개발자 도구로 우회 가능 → 최종 방어선!)

Prisma — SQL 없이 DB 다루기

Prisma를 쓰면 TypeScript 코드로 DB를 조작합니다. SQL을 몰라도 됩니다!

Prisma CRUD 예시 // 생성 (Create) await prisma.user.create({ data: { email: 'a@b.com', name: '홍길동' } }); // 목록 조회 (Read) await prisma.user.findMany({ where: { type: 'ADMIN' }, // 조건 orderBy: { createdAt: 'desc' }, // 정렬 skip: 0, take: 20, // 페이지네이션 }); // 단일 조회 await prisma.user.findUnique({ where: { id: 'abc123' } }); // 수정 (Update) await prisma.user.update({ where: { id: 'abc123' }, data: { name: '김철수' } }); // 삭제 (Delete) await prisma.user.delete({ where: { id: 'abc123' } });

전체 요청 흐름

api.post('/users', data) 호출 시 일어나는 일:

1️⃣ 프론트엔드
api.post('/users', { email, password, name })
Authorization 헤더에 JWT 토큰 자동 첨부
↓
2️⃣ JwtAuthGuard
JWT 토큰 검증 — 유효하면 통과, 무효하면 401
↓
3️⃣ PermissionsGuard
user:create 권한 확인 — 있으면 통과, 없으면 403
↓
4️⃣ DTO 검증
이메일 형식, 비밀번호 8자 이상 — 통과하면 Controller로
↓
5️⃣ Controller → Service
중복 확인 → 비밀번호 암호화 → DB 저장 → 역할 할당
↓
6️⃣ 응답 반환
{ id, email, name, roles: [...] } → 프론트엔드에서 수신

Guard — 보안 관문

Guard는 요청이 Controller에 도달하기 전에 체크하는 보안 관문입니다.
React의 AuthGuard 컴포넌트와 같은 역할입니다.

📨 요청
→
🔑 JwtAuthGuard
"로그인했나?"
→
🛡️ PermissionsGuard
"권한이 있나?"
→
🚪 Controller
"처리 시작"

NestJS Guard 적용

// 클래스 전체에 로그인 필수 @UseGuards(JwtAuthGuard) export class UserController { // 특정 메서드에만 권한 체크 추가 @Post() @UseGuards(PermissionsGuard) @Permissions('user:create', '*') create() { ... } }

React Guard 비교

// React의 AuthGuard <Route path="/" element={ <AuthGuard> <AdminLayout /> </AuthGuard> } > <Route index element={<Dashboard/>} /> </Route>

Module — 모든 것을 조립하는 곳

user.module.ts @Module({ imports: [PrismaModule, RoleModule], // 다른 모듈의 기능 가져오기 controllers: [UserController], // 요청을 처리할 컨트롤러 providers: [UserService], // 비즈니스 로직 서비스 exports: [UserService], // 다른 모듈에서 쓸 수 있게 공개 }) export class UserModule {}
📌 마지막 단계 — AppModule에 등록
React에서 App.jsx에 <Route>를 추가하는 것처럼, NestJS에서는 AppModule에 새 모듈을 등록해야 합니다.
app.module.ts @Module({ imports: [ PrismaModule, AuthModule, ContentTypeModule, ContentModule, MediaModule, RoleModule, UserModule, // ← 여기에 추가! 이게 없으면 /users API 작동 안 함 DashboardModule, TasksModule, ], }) export class AppModule {}
